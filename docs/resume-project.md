## 简历项目描述

### 一行版本

**RepoCoach FE | AI 驱动的 GitHub 项目深挖与前端面试训练平台**

线上演示：<https://repocoach-web.onrender.com>  ·  API：<https://repocoach-api.onrender.com/api/v1/health>

### 两到三行版本

基于 Next.js、NestJS、PostgreSQL 和 DeepSeek 构建代码证据驱动的项目面试 Agent。固定 GitHub 代码版本，以受限 Tool Calling 按需取证，通过引用校验的四项 Rubric 评价回答；将回答、取证和评分拆为持久化阶段，支持断点恢复、幂等提交与仅重试评分，最终生成训练复盘与能力报告。

### 技术亮点

- 使用 Next.js 14 + TypeScript 构建响应式工作台，包含注册登录、仓库导入、连续问答、复盘导出和能力报告等完整用户流程。
- 使用 NestJS 编排模型取证循环，提供搜索、阅读与词法结构工具，以 commit/blob SHA 固定来源，校验路径与参数，限制调用次数、读取范围、结果大小和总耗时。
- 将不可改写回答与取证 checkpoint 保存到 PostgreSQL，以租约 token 和条件更新限制竞争写入；评分重试复用原证据，最终评价、完成状态与题号通过 Prisma 事务原子提交。
- 实现正确性、代码依据、技术取舍、失败边界四项 Rubric 与证据 ID 校验，服务端计算加权分；证据不足保留分项理由，不纳入能力均分。提供20条合成样例与可复现评测脚本。
- 设计按run连续排序的执行事件与SSE断线补发，业务状态和事件同事务提交；从有据模型评价生成可追溯练习计划，以用户epoch处理清除记忆与旧任务完成的竞争。
- 使用 Prisma + PostgreSQL 设计用户、会话、面试和回答关联模型；通过 HttpOnly Cookie 与按 userId 查询实现会话管理和数据隔离。
- 配置 Docker Compose 编排 Web、API、PostgreSQL，加入健康检查和自动 Prisma 迁移；通过 GitHub Actions 执行 Prisma 生成、Lint、API 测试和生产构建。

## 30 秒介绍

我做了一个基于真实代码的项目面试 Agent。它导入公开 GitHub 项目并固定版本，围绕实际文件提问，通过受限工具查证回答，再从正确性、代码依据、取舍和失败边界四项给出带引用的评价。工程上把回答、取证和评分分开持久化：模型评分失败时能复用已完成的证据，刷新或重启也能恢复。证据不足就不给总分。我还提供了真实数据库恢复测试和20条合成评分样例，人工校准与线上质量评测还没有完成。

## 高频追问与回答方向

### 为什么不在浏览器直接调用 DeepSeek 和 GitHub API？

密钥不应暴露在浏览器，仓库分析和模型调用也需要统一的限流、错误处理和输入边界。因此浏览器只调用 NestJS API，服务端再访问第三方服务。

### 如何防止用户 A 看到用户 B 的训练记录？

认证成功后服务端将随机 session token 写进 HttpOnly Cookie，只保存 token 哈希。SessionGuard 从 Cookie 恢复用户；所有面试和报告查询都带上 userId 条件，数据库关系还使用级联删除。

### AI 返回不符合预期怎么办？

评分结构、分项范围和证据 ID 都必须通过服务端校验，无效结果不能标为成功。超时、网络错误或校验失败会将当前阶段保存为失败，不推进题号；用户可在三次尝试上限内重试。取证成功后评分失败只重试评分，不再读取 GitHub。没有配置模型时才使用无分演示。最终数据库提交失败会整体回滚；模型缺失追问则使用保存的候选题，不提前结束业务流程。

### 为什么租约和事务不能保证模型只调用一次？

进程可能在模型已经返回、数据库尚未保存时崩溃。过期租约的接替者只能看到上一个 checkpoint，必须重新执行该阶段，因此外部调用至少一次。租约 token 拦截旧 worker 写入，唯一约束与事务保证只有一个最终题目结果。取证 checkpoint 能避免评分重试重复读取代码，但不能保证取证内部每个工具只执行一次。

### 怎样说明评分器的评测结果？

20条合成样例覆盖优秀、含糊、错误、注入和证据缺失，脚本记录格式、引用、排序、延迟和 Token。Prompt v2 在该集上20条都通过格式与引用检查，12组排序符合初始预期。样例尚无人工复核，也没有独立留出集，所以不能称为100%评分准确率。

### 为什么选择 Prisma 和 PostgreSQL？

训练数据有明确的用户、会话、面试、回答关系，适合关系型数据库。Prisma 提供类型安全查询、迁移历史和可读的数据模型；PostgreSQL 更适合后续在云端部署与扩展，而不是把数据留在本地 SQLite 文件中。

### Docker 部署中如何保证启动顺序？

Compose 先等待 PostgreSQL health check 通过，API 启动命令应用 Prisma 迁移，然后 Web 等待 API health check。这样避免 API 在数据库未就绪时启动失败。

## 可现场演示的流程

1. 注册一个新账号，演示 Cookie 登录态和账号工作区。
2. 导入公开 GitHub 仓库，展示识别出的技术栈与关键文件。
3. 开始训练，展开绑定源码，提交回答并展示取证/评分阶段。
4. 展开四项评分理由及其源码引用，解释无法判断为何不产生能力总分。
5. 打开训练复盘、能力报告和 Markdown 导出。
6. 展开执行过程，演示SSE断线补发、训练计划来源和清除记忆。
7. 用专用临时账号fixture演示仅重试评分，明确故障由测试注入。
8. 展示单元测试、真实数据库恢复测试、合成评测和已通过的GitHub CI结果。

## Agent 应用工程岗位的表述

基于 Next.js、NestJS、PostgreSQL 和 DeepSeek 构建代码证据驱动的项目面试 Agent。设计受限 Tool Calling 与 commit/blob 固定的取证流程；通过四项 Rubric、证据 ID 校验和服务端加权计算形成可复盘评价。以 PostgreSQL 持久化阶段、租约和事务实现会话恢复、幂等提交与仅重试评分，配套合成评测和真实数据库故障验证。

可深入讲解：幂等与至少一次调用、checkpoint位置、旧worker写入屏障、SSE序号与补发、记忆清除epoch及引用的语义边界。68项API单元测试、4项前端请求边界测试、10个PostgreSQL场景与8个完整HTTP流程场景及Linux CI已通过；真实线上四题、SSE补发、浏览器复盘/导出和记忆清除已验证，评分质量仍需人工标注集评测。现场演示见[演示手册](demo-guide.md)，发布成效见[升级总结](release-summary.md)。

本项目与通用终端 Coding Agent 互补：后者展示工具执行环境与权限，RepoCoach 展示领域取证、可解释评价和业务状态恢复。不要将合成场景结果表述为真实业务评分质量提升。
